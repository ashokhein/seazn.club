# W6 — z3 Minimal-Movement Repair Engine — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Repair an AI-proposed schedule to verifier-clean with the *fewest possible fixture moves*, using z3 as an in-process WASM solver, falling back to LLM repair on a finite wall-clock budget.

**Architecture:** A new pure engine module `packages/engine/src/scheduling/repair.ts` (plus its pure domain builder `repair-domain.ts`) encodes the hard scheduling rules over integer **minutes-since-epoch** and asserts them to z3. It **imports every rule semantic from `calendar.ts`** — rest amounts, scope coverage, selector resolution, merged hard-rule stream — and never re-derives one. Minimality comes from an ascending search on *k* = number of fixtures allowed to move, using solver `push`/`pop`; the first satisfiable *k* is the minimum by construction. Constraint families are asserted under **assumption literals**, so an UNSAT check yields a core naming *which families cannot hold together*. `repairAndVerify` re-runs the real verifier on the solver's output and throws if it is not clean. Both AI runners (single-division `schedule-ai.ts`, joint `competition-schedule-ai.ts`) try the solver **before** spending an LLM repair round and report which engine repaired the board in telemetry.

**Tech Stack:** TypeScript (ESM, raw TS source consumed by Next), `z3-solver@5.0.0` (official WASM build, in-process, lazy `await import`), vitest, Playwright (e2e), Next 16 App Router.

## Global Constraints

Copied verbatim from issue #401, the design doc (§3, §6, §8), and repo rules. Every task inherits these.

- **NO fixture-count gate.** Solve the full `COMPETITION_MOVABLE_CAP = 500` movable range. Higher latency on large boards is accepted.
- **Termination is the real bound.** A finite wall-clock solver budget is mandatory, with a **telemetry-visible fallback to LLM repair** on timeout. Never fall back to silence, and never present an unrepaired plan as repaired.
- **Determinism is a requirement.** Fixed random seed, fixed variable ordering, pinned solver version (`"z3-solver": "5.0.0"` — **exact, no caret**). Same input → same output, asserted by test.
- **Do not fork rule semantics into the solver.** If the solver needs a definition `calendar.ts` does not export, **export it from `calendar.ts`** — that is the whole point of the placement rule.
- **z3 is lazy.** `await import("z3-solver")` inside the solve path only. The LLM-only path (and a proposal that is already clean) must never load the WASM.
- **z3 is NOT a sub-processor** (in-process WASM, no personal data leaves the process). No legal/DPA work is owed by this wave.
- **Minimal movement is a safety property, not an optimisation.** It is what makes repair safe against already-published schedules. Never trade it for a faster objective.
- **Drop-and-mark-unschedulable stays upstream.** The solver never chooses which fixtures to drop; on genuine overflow it returns `infeasible` with the families named and the caller decides.
- Every change ships a test that **fails without it**.
- Any new or changed user-facing string → **all 4 locale dictionaries** (`apps/web/src/dictionaries/{en,fr,es,nl}/ui.json`), never hardcoded English. Then `npm run gen-keys` and `npm run i18n:check`.

- **api-v1 schema change → `npm run openapi:gen` + commit `openapi/*.json`.** The drift gate is CI-only; a green local run proves nothing. Adding a field to the AI-plan response **will** trip it.

```ts
// packages/engine/src/scheduling/z3-load.ts
// z3 is loaded LAZILY and ONCE (#401). The WASM must never touch the LLM-only
// path: a proposal that verifies clean, or a run that falls back to LLM repair,
// pays nothing for a solver it does not use. `z3LoadCount` exists so that
// property is a test rather than a promise.
//
// Determinism is configured HERE, not at the call site, so every solver in the
// process shares one seeded, single-threaded configuration.
export interface Z3Context {
  // Deliberately loose: z3-solver's generic `Context<Name>` types do not survive
  // being handed around, and the encoder uses only the documented surface.
  Z3: any;
  shutdown: () => void;
}

let loaded: Promise<Z3Context> | null = null;
let count = 0;

export function z3LoadCount(): number {
  return count;
}

export async function loadZ3(): Promise<Z3Context> {
  if (loaded !== null) return loaded;
  count++;
  loaded = (async () => {
    const { init } = await import("z3-solver");
    const { Context, em, setParam } = await init();
    // Single-threaded and unseeded-free: parallel portfolio solving picks
    // whichever thread finishes first, which is exactly the "the solver felt
    // different today" support ticket this wave refuses to file.
    setParam("parallel.enable", false);
    setParam("sat.random_seed", 0);
    setParam("smt.random_seed", 0);
    setParam("nlsat.seed", 0);
    return {
      Z3: Context("repair"),
      shutdown: () => em.PThread.terminateAllThreads(),
    };
  })();
  return loaded;
}

/** Test-only: drops the singleton and stops the worker threads node keeps alive. */
export async function resetZ3(): Promise<void> {
  if (loaded === null) return;
  const ctx = await loaded;
  ctx.shutdown();
  loaded = null;
  count = 0;
}
```

```ts
export function pairRestMinutes(config: VerifyConfig, a: Assignment, other: Assignment): number {

    if (h.type !== "min_rest_minutes" || h.rest_scope === "feeder_to_dependent") continue;

      scopeCoversFixture(h.scope, fixtureById.get(a.fixtureId), a) ||
      scopeCoversFixture(h.scope, fixtureById.get(other.fixtureId), other);
    if (covers) minutes = Math.max(minutes, h.minutes);
  }
  return minutes;
}
```

Structure (write it in this order — the order is the reasoning):

```ts
// packages/engine/src/scheduling/repair-domain.ts
// The z3-free half of repair (#401). Every calendar decision — which day a
// fixture may fall on, what "not before 18:00" means in the org zone, how long
// a DST day is — is made HERE, in TypeScript, against `tz.ts` and the rule
// semantics `calendar.ts` exports. z3 then sees nothing but integers.
//
// Why not encode day/HH:mm arithmetic symbolically: a calendar day is 23, 24 or
// 25 hours long and a wall-clock bound moves with it, so the symbolic form
// needs a timezone database inside the solver. Discretising into absolute
// intervals at encode time keeps ONE timezone implementation in the process —
// the verifier's.
```

Implementation notes the engineer must honour:

- `dayBuckets`: if `sessionWindows` is non-empty, each session window **is** a bucket (they are absolute instants and are the documented escape hatch for a division whose zone differs — design §8). Otherwise, walk `window` day by day: `ymd = dayKeyInTz(cursor, tz)`, `from = max(window.from, zonedTimeToUtc(ymd, "00:00", tz))`, `to = min(window.to, zonedTimeToUtc(ymdAddDays(ymd, 1), "00:00", tz))`, then `cursor = to`. **Never `cursor + 86_400_000`.** If `tz` is undefined, return a single bucket for the whole window (matching the verifier, which skips every day-shaped rule without a zone).
- Per fixture, per family, produce start-intervals by clipping each bucket:
  - `window` — the pack window, minus `durationMs` at the tail.
  - `blackout` — buckets minus global blackout intervals; **court-scoped** blackouts remove the *court* from `courtsByFamily.blackout` only when that blackout covers every bucket, otherwise they are emitted as court-conditional intervals the encoder asserts under `court == c`. Keep it simple and correct: return `courtIntervals: Record<string, Interval[]>` for the blackout family and let the encoder build the implication.
  - `start_window` — `startWindowFor(config, a)` clipped onto the buckets.
  - `instruction` — from `effectiveHard(config)`:
    - `fixture_on_date` / `fixture_on_weekday`: keep only buckets whose `ymd` matches (`weekdayOfYmd(ymd)`), for fixtures named by `resolveSelector(h.selector, h.scope, ruleFixtures)`, filtered by `scopeCoversFixture`.
    - `not_before` / `not_after`: clip each bucket to `[zonedTimeToUtc(ymd, h.time, tz), bucketEnd]` / `[bucketStart, zonedTimeToUtc(ymd, h.time, tz)]`. `not_after` bounds the **start**, so do **not** subtract the duration from it — the verifier compares `hhmmInTz(a.startAt)`.
  - `session windows` fold into `window` (the verifier reports both as one bound).
- Intersect intervals family-by-family; a family whose result is empty goes into `empty`, and the caller reports it without ever loading z3.
- `candidatePairs` returns index pairs whose *intersected* domains (across all families) overlap by more than `-durationMs`, i.e. where a clash is arithmetically possible. This is the O(n²) pruner that keeps 500 movable fixtures tractable.
- Sort every output by `fixtureId` — **determinism starts here**, before z3 sees anything.

```ts
export const REPAIR_FAMILIES = [
  "window", "blackout", "court", "rest", "person", "order", "instruction", "start_window",
] as const;
export type RepairFamily = (typeof REPAIR_FAMILIES)[number];

/** Minutes. The lattice repaired starts snap to; a fixture's ORIGINAL start is
 *  always legal even when it is off-grid, so k=0 is always representable. */
export const REPAIR_GRID_MINUTES = 5;

export interface RepairInput {
  proposal: readonly Assignment[];              // the fixtures this run may move
  existing?: readonly Assignment[];             // immovable board + obstacles
  dependencies?: readonly OrderDependency[];
  config: VerifyConfig & { courts: readonly string[] };
  budgetMs?: number;                            // default DEFAULT_REPAIR_BUDGET_MS
  gridMinutes?: number;
  onProgress?: (p: { k: number; elapsedMs: number }) => void;
}

export type RepairResult =
  | { status: "clean";      assignments: readonly Assignment[]; moved: readonly string[]; k: 0; elapsedMs: number; checks: number; relaxed: readonly RepairFamily[] }
  | { status: "repaired";   assignments: readonly Assignment[]; moved: readonly string[]; k: number; elapsedMs: number; checks: number; relaxed: readonly RepairFamily[] }
  | { status: "infeasible"; families: readonly RepairFamily[]; elapsedMs: number; checks: number }
  | { status: "timeout";    lastK: number; elapsedMs: number; checks: number };

export async function repairSchedule(input: RepairInput): Promise<RepairResult>;
```

**Encoding contract (the reasoning, so the implementer does not invent a different one):**

| Element | Encoding |
|---|---|
| time unit | **minutes since epoch**, `Int`. Absolute ms would work (z3 ints are arbitrary precision) but minutes keeps the literals small and matches every rule's unit. |
| `start_i` | one `Int` per movable fixture, created in `fixtureId` sort order |
| grid | `Or(start_i % grid == 0, start_i == origStart_i)` — the original placement is always legal so *k*=0 is representable even when the LLM placed off-grid |
| `court_i` | one `Int` per fixture, `0 <= court_i < courts.length`; index into the **sorted** court list |
| duration | constant per fixture (`endAt - startAt`). Repair moves fixtures; it never resizes them. |
| domain | `Or` over Task 3's intervals, asserted **per family** under that family's assumption literal |
| court clash | for each candidate pair: `court_i == court_j → (end_i + gap <= start_j ∨ end_j + gap <= start_i)`; mirrors `courtBlocked`'s gap padding, half-open |
| rest / overlap | for each pair sharing an entrant or a person, separation `>= R`, where **R depends on whether both sides can move** (see below). Rest ≥ 0 subsumes overlap, so `person` and `rest` share one arithmetic form under two assumption literals (`person` when rest is 0, `rest` when it is positive) |

**R is NOT always the max — this bit is easy to get wrong and the verifier will catch you.**
`validateAssignments` loops `for (const a of assignments)` over `board = [...existing, ...assignments]`, so:

- **movable vs movable** — both orderings are evaluated, so the pair owes
  `R = max(pairRestMinutes(c, i, j), pairRestMinutes(c, j, i))`.
- **movable vs immovable (`existing`)** — only the movable side is ever the outer `a`, so the
  pair is judged **one-directionally** and owes exactly
  `R = pairRestMinutes(c, movable, immovable)` — that argument order, no max.

Assert the max against an immovable and the solver over-constrains, returning a spurious
`infeasible` on a board that is actually fine. Assert the wrong single direction and it
under-constrains, and `repairAndVerify` throws on a board the solver thought was clean.
`pairRestMinutes` is asymmetric because `effectiveRestMinutes` reads the **first**
argument's pool/division.
| order deps | `start_target >= end_source + effectiveRestMinutes(config, target)` — the feeder-rest semantic from `calendar.ts:984`, not a re-derivation |
| immovables | the same constraints against **constants** (their fixed start/court) |
| `max_fixtures_per_day` | `onDay[i][d]` Bool ⟺ `start_i ∈ bucket_d`; `AtMost([...scoped bools], count - immovableOnDay_d)`. Only created when such a rule exists. |
| movement | `moved_i` Bool ⟺ `Or(start_i != origStart_i, court_i != origCourtIdx_i)`; minimality is `AtMost(moved, k)` |

**Search:**

1. If `validateAssignments(proposal, config, existing, dependencies)` is empty → return `{status:"clean"}` **without loading z3**. This is the property Task 1's `z3LoadCount` test guards.
2. Load z3, build the encoding once.
3. **Feasibility probe first:** `check(...allFamilies)` with **no** `AtMost` bound. UNSAT here means no amount of movement helps → go to step 5. This one check saves walking *k* on a genuinely impossible board.
4. Ascending *k* = 0,1,2,…,n with `push()` / `AtMost(moved,k)` / `check(...families)` / `pop()`. First `sat` is the minimum **by construction**. Call `onProgress` each iteration — the *k* the loop is on is a legible progress signal for large solves.
5. On UNSAT at step 3: re-check with only the **blocking** families (`court`, `person`, `window`, `order`) to see whether a physically-possible board exists at all. If that is sat, run the ascending-*k* search under those families and return `relaxed` = the families dropped. If it is unsat too, return `{status:"infeasible", families}` from `[...solver.unsatCore()]` mapped back from assumption name → family.
6. **Budget:** before every `check()`, `solver.set("timeout", Math.max(0, budgetMs - elapsed))`; if the remaining budget is ≤ 0, or `check()` returns `"unknown"` with `reasonUnknown() === "timeout"`, return `{status:"timeout", lastK}`. Never throw on a budget exhaustion — the caller's fallback is the designed behaviour.

## Self-review

**Spec coverage.** Every acceptance criterion on #401 maps to a task: Stepladder repair → T4; golden + one clash, exactly one move → T4; `repairAndVerify` throws → T5; infeasible names families → T4; determinism → T4; timeout → LLM fallback visible in telemetry → T4 (engine) + T8/T9 (telemetry); lazy WASM → T1 + T4; measured 50/120/250/500 and budget from evidence → T6; a 500 board never hangs → T6. Design §6's cross-cutting rules → T10 (openapi), T11 (i18n), T12 (e2e, smoke, help).

**No placeholders.** The two spots that intentionally carry a value rather than a literal are `DEFAULT_REPAIR_BUDGET_MS` (T6 — it is *defined* to be the measured number) and the golden 13-slot triple list in T4's helper (it is read from the existing golden schedule in the repo, not invented).

**Type consistency.** `RepairFamily` is declared once in `repair.ts` and imported by `repair-domain.ts`; `RepairInput.config` is `VerifyConfig & { courts }` everywhere; `repair` telemetry is snake_case to match the existing `usage` shape (`input_tokens`, `repair_rounds`).

**Known risk, deliberately accepted.** The domain builder discretises calendar rules into absolute intervals at encode time. If that discretisation and the verifier ever disagree, `repairAndVerify` throws rather than shipping a bad board — loud, not silent. That is the designed failure mode.
